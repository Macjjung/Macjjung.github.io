# Portfolio References

## 1. 구성·정보 배치의 주 레퍼런스

- 자료: 사용자 제공 포트폴리오 PDF
- 표준 경로: `docs/references/portfolio-reference.pdf`
- 열기: [레퍼런스 PDF](references/portfolio-reference.pdf)
- 용도: 내부 구성·정보 배치 참고. 웹·배포 파일에 포함하지 않는다.
- 상세 페이지 구성: [STRUCTURE-PROPOSAL.md](STRUCTURE-PROPOSAL.md)

PDF에서 도입부의 분리, 프로젝트별 표지, 문제·판단·실행의 대응 관계, 설명과 근거의 인접 배치를 참고한다. 원본은 23쪽이지만 우리 포트폴리오는 구조 제안서의 15장을 따른다. PDF의 색·장식·기여도 배지·마무리 페이지까지 복제하지 않는다.

### 실제 이미지 확인 기록 — 2026-11-10

PDF 23쪽을 PNG로 렌더링하여 1–23쪽 전체를 페이지 번호가 있는 축소 모음 이미지로 확인했다. 4·6·7·9·21쪽은 개별 1200×675 이미지로 확대 확인했다. 텍스트 추출만으로 배치를 판단하지 않았다. 최초 Poppler 출력에서 한글 매핑 경고가 발생하여 PDFium으로 전 페이지를 다시 렌더링한 이미지를 기준으로 검토했다.

- 1–3쪽: 전체 표지, About Me, Contents를 별도 페이지로 구성. About Me는 프로필·교육과 경력·역량을 좌우로 나누고, Contents는 프로젝트명을 독립 항목으로 보여준다.
- 4·11·17쪽: 프로젝트별 표지. 제목과 짧은 설명, 기여도 또는 기간 등 프로젝트 정보가 본문과 분리되어 있다. 우리는 기여도 백분율 대신 확인된 기간·역할과 핵심 역량 하나를 쓴다.
- 5–6쪽: 문제의 근거와 개편 방향. 특히 6쪽은 문제 → 해결 방향 → 개편 과제를 행별로 대응시킨다. 우리 콘텐츠의 문제 → 판단 → 실행 관계에 적용한다.
- 7–8쪽: 실제 화면의 변경 전후를 설명 가까이에 배치한다. 7쪽은 두 개선 영역을 좌우로 구분하고 각 영역에서 전후 화면을 비교한다.
- 9–10쪽: 협업·실행 과정과 결과를 구분하고, 성과와 회고를 별도 정보 영역으로 제시한다. 타인의 지표·기여도는 가져오지 않는다.
- 12–16쪽: 문제·가설·검증·해결안·회고의 단계 라벨과 자료 배치. 원본에 가상 인터뷰·예상 성과가 있으므로, 우리 사례에서 실제 수행한 검증이나 관찰 성과로 전용하지 않는다.
- 18–22쪽: 배경·접근 방법·결과·개선사항·한계를 구분한다. 21쪽은 설명 옆에 화면과 메뉴 구조 자료를 배치한다. 자료가 없는 우리 페이지에는 빈칸과 짧은 이미지 예시만 둔다.
- 23쪽: 마무리 표지. 우리 15장에는 별도 마무리 페이지를 추가하지 않는다.

### matching-journey 결과 페이지 참고 — 2026-11-10

- 실제 이미지 확인: 9쪽과 20쪽의 1200×675 PNG를 열어 확인했다. 렌더링 원본과 현재 PDF의 SHA-256이 같은 `846e6e6acfc4edd0f923d95bd49786971a043fc717cef07f343cc17a3801394f`임을 대조했다.
- 9쪽: 상단의 제목·짧은 설명 아래 좌우 본문이 같은 높이에서 시작한다. 수치와 의미 설명이 붙어 있고 항목 사이 간격은 일정하다. 수치 옆에 해석을 붙이는 원칙만 적용하며 카드 반복·색면·타인 수치는 복제하지 않는다.
- 20쪽: 분석 대상마다 가로 영역을 나누고 각 영역 제목 가까이에 근거를 배치한다. 제목보다 작은 수치와 설명, 영역 사이 여백으로 읽는 순서를 만든다. 전송 효율·소비 / 서비스 전체 / 후속 전환의 분리 원칙으로 적용한다.
- 이번 점검에서 표준 경로 사본이 없어 원본 `portfolio-reference..pdf`를 보존한 채 `portfolio-reference.pdf`를 다시 생성했다. 두 파일의 SHA-256은 동일하며 배포에서는 제외한다.

### 적용 원칙

- 전체 표지 → About Me → Contents → 프로젝트 3개 × 각 4장.
- 프로젝트별 프로젝트 표지 → 문제와 판단 → 실행 내용 → 결과.
- 프로젝트 표지: 프로젝트명, 내가 수행한 내용 한 문장, 핵심 역량 하나, 확인된 기간과 역할.
- 감성적 슬로건·추상적 자기평가 없이 사실로 설명한다.
- 숫자·시각화를 과도하게 크게 만들지 않는다. 필요한 크기의 표·차트·실제 화면과 짧은 설명을 함께 둔다.
- 레퍼런스의 경력·수치·기여도·고객 정보·가상 검증을 지원자의 사실로 사용하지 않는다. 내 콘텐츠·성과의 기준은 CONTENT.md다.

### 파일 관리

표준 경로는 `docs/references/portfolio-reference.pdf` 하나로 통일한다. 이번에 프로젝트 안에서 발견한 원본을 유지한 채 표준 경로로 복사했다. 원본과 사본의 SHA-256은 동일하다: `846e6e6acfc4edd0f923d95bd49786971a043fc717cef07f343cc17a3801394f`.

표준 경로에 같은 파일이 있으면 추가 사본을 만들지 않는다. 원본 파일명은 작업 지침의 참조 경로로 사용하지 않는다. 내부 PDF 및 렌더링 이미지는 assets에 넣거나 배포 패키지에 포함하지 않는다. PDF는 Git에도 올리지 않는 로컬 자료다. 새 체크아웃에서는 사용자가 제공한 원본을 표준 경로에 배치해야 한다.

## 4. 문서별 기준

- 목적·독자·15장 구성 개요: BRIEF.md.
- 실제 수행·수치·비교 조건·성과 귀속: CONTENT.md.
- 페이지별 상세 내용·배치: STRUCTURE-PROPOSAL.md.
- 구성·정보 배치 참고: 이 문서와 지정 PDF.
- 1920×1080, 16:9, 공통 정렬·폰트·컬러·검수: DESIGN_SYSTEM.md.

레퍼런스의 타인 사실이나 시각적 표현이 콘텐츠 기준을 바꿀 수 없다. 공통 캔버스·헤더·푸터는 유지하며, 한 줄·두 줄 제목 공통 변형을 사용한다.

## 5. 적용 절차

1. BRIEF.md, CONTENT.md, STRUCTURE-PROPOSAL.md의 목적·사실·페이지 구성을 확인한다.
2. 지정 PDF의 실제 페이지를 이미지로 확인하고 해당 페이지 번호와 적용할 배치 원칙을 기록한다.
3. 문제·판단·실행·결과와 각 근거 자료를 대응시킨다. 필요 시 Riddes의 보조 시각 요소와 쿠팡 컬러를 참고한다.
4. 웹 구현 요청을 받은 경우에만 DESIGN_SYSTEM.md를 적용해 표지·문제/판단·실행/결과의 대표 페이지부터 구현한다.
5. 실제 렌더링을 검토한 뒤 공통 패턴을 나머지 페이지에 적용한다. 확인하지 못한 검증은 미검증으로 표시한다.

단순 문구 수정은 불필요한 레퍼런스 재조사를 하지 않는다. 이번 작업은 참고 자료·지침 정리에 한정하며 웹 화면은 변경하지 않는다.
